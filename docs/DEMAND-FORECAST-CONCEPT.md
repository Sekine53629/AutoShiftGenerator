# 需要予測による人員配分 — 次期プロジェクトの構想案

2026-09-04 記録。**構想であって、着手の予定ではない。**

いまの移植（`GAS-PORTING-SPEC.md`）と要件（`REQUIREMENTS.md`）の範囲外。
本移植が終わったあとに、別の変更として検討する。

---

## 1. なぜ要るか

シフト作成は、**クリニックの診療体制が確定する前に着手することがある**。
いまの仕組みは医師数（`医師数(診)` 行）を必要人数の唯一の駆動因子にしているので、
医師数が未入力の日は必要人数が出せない。

```
必要数 = 医師数 + n        （n は 自動作成設定 L列「必要出勤数(医師数+n)の n」）
```

医師数が埋まるのを待たずに組めるようにしたい。

---

## 2. 何が予測に効くか（現場の見立て）

シフト担当者の見立てとして、次の順で効く。

1. **処方日数と次回予約日** — 最も強い。処方箋に書かれている
2. **予約は7の倍数に寄る** — 28日、30日、32日など。28日処方が特に多い
3. **処方日数 + 手持ちの残薬日数** で、より確かな来局日が出せる
4. **曜日** — 診療体制そのものが曜日で決まっている

医師の出勤は予約に合わせて決まるので、**来局の山が読めれば医師数も読める**。
つまり「処方箋枚数 → 必要薬剤師数」を直接当てにいくより、
「来局日 → 診療体制 → 必要人数」の順に辿るほうが筋がよい。

---

## 3. 段階

### 段階1: 曜日別の標準診療体制 ★これは予測ではない

「月曜は5診、日曜は3診」のような**標準体制を設定として持ち、
医師数が未入力の日をそれで埋める**だけ。

- 予測モデルではなく**設定テーブル**。統計もデータの蓄積も要らない
- いますぐ実装できる。`自動作成設定` に曜日 × 標準医師数の欄を足すだけ
- 「なぜこの人数か」を完全に説明できる
- **医師数が入力されたら必ずそちらを優先する。**設定値はあくまで穴埋め

シフト確定前に着手したい、という当初の困りごとは**これでほぼ解ける**。
段階2以降に進まなくても価値がある。

### 段階2: 28日周期の再来予測

処方日数の分布から「N 日後に何人戻ってくるか」を積み上げる（畳み込み）。

```
ある日の来局見込み = Σ（d 日前の処方箋枚数 × その日に処方日数 d が占めた割合）
```

**いまのデータでは計算できない。**日報アプリが持っているのは
`処方箋枚数`（件数）だけで、**処方日数の内訳が無い**。
段階2に進むなら、日報アプリ側に「処方日数別の枚数」または
「平均処方日数」を記録する項目を足す必要がある。★別プロジェクトへの依存

### 段階3: 蓄積したデータでモデルを育てる

日報の記録が貯まってから。曜日・祝日前後・月初月末・季節性を足していく。

**説明できる形に留めること。**この出力は人の休みを決める。
「なぜこの日は3人なのか」を答えられない仕組みは労務に乗らない。
係数の見える回帰までにして、ブラックボックスには踏み込まない。

---

## 4. 設計上の接ぎ口

**配置エンジンには手を入れない。**

エンジンが見るのは `input.days[].required` だけで、
これを作っているのは `ShiftAuto.buildDayInfo_()` の1関数。
予測を入れるとしても、差し替えるのはここだけになる。

```
                     ┌─ 医師数（入力済み）      ← いつでも最優先
required の作り方 ───┼─ 曜日別の標準体制        ← 段階1
                     ├─ 再来予測                ← 段階2
                     └─ モデル                  ← 段階3
                              │
                              ▼
                     Engine.runEngine(input)   ← ここは変えない
```

この形を保つ限り、予測の実装は移植の検証を壊さない。

---

## 5. 移植の検証との関係 ★重要

移植の正しさは「**同じ入力なら VBA と同じ出力**」で確かめる（仕様書 §9 フェーズ3）。

`required` を予測値にすると、**定義上その検証はできなくなる**。
だから順序を守る。

1. 医師数から `required` を作る形で移植を終え、VBA 版と突き合わせる
2. **検証が済んでから**、`required` の作り方に選択肢を足す
3. 予測を使うときも、医師数が入力されている日は必ず医師数を優先する

**代理指標で本物を置き換えない。**処方箋枚数は医師数の代理であって、
医師数が手に入らないときのつなぎ。確定したら本物に戻す。

---

## 6. 引っかかっている点

| | |
|---|---|
| **データ量** | 日報アプリの稼働は 2026 年夏。季節性を見るには足りない |
| **データ項目** | 処方日数が記録されていない。段階2には日報アプリ側の変更が要る |
| **別プロジェクト依存** | `DailyReportApp` は別リポジトリ・別ブック。実行時に読むなら `IMPORTRANGE` か Sheets API になり、権限と結合が増える |
| **診療体制の変化** | クリニックの体制が変われば過去のデータは効かなくなる。モデルは常に「最近」を重く見る形にする |
| **説明責任** | 労務に関わる。係数が見える形に留める |

---

## 7. いま決めなくてよいこと

段階1（曜日別の標準体制）だけは、移植中に**置き場所を用意しておく価値がある**。
`自動作成設定` に欄を足しておけば、あとから読むだけで済む。

段階2以降は、日報アプリのデータ項目が決まってから考える。
