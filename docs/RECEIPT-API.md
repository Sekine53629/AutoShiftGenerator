# レセコン連携の受け口

レセコン（シグマ）から日次の実績を受け取るための **こちら側の仕様**。

ベンダーとの交渉は「何が出せますか」から始めると話が発散する。
**こちらが受け取れる形を先に決めておけば、「この形に寄せられますか」で済む。**
実装より先にこの契約を固める。

> 何を溜めるかは [FEATURE-COLLECTION.md](FEATURE-COLLECTION.md) を参照。

---

## 1. 受け取る形（正規形）

**ベンダーに依存しない形をこちらで定義し、変換はアダプタが担う。**
シグマの出力形式がどうであれ、この形に直してから中へ入れる。
将来レセコンを替えても、アダプタを差し替えるだけで済む。

```json
{
  "source": "sigma",
  "fetchedAt": "2026-10-02T09:15:00+09:00",
  "records": [
    {
      "storeCode": "SAPPORO-01",
      "date": "2026-10-01",
      "counts": {
        "prescriptions": 118,
        "newPatients": 9,
        "onePack": 12,
        "mixing": 4,
        "compounding": 2,
        "duplicationCheck": 3,
        "narcotics": 1,
        "homeVisit": 2,
        "internalDrugUnits": 214
      },
      "dispenseDays": { "7": 12, "14": 30, "28": 41, "30": 18, "56": 9, "90": 8 },
      "byDoctor": [
        { "doctorCode": "DR001", "prescriptions": 34 },
        { "doctorCode": "DR002", "prescriptions": 28 }
      ]
    }
  ]
}
```

### 項目の定義（ここを曖昧にしない）

| キー | 内容 | 単位の確認事項 |
|---|---|---|
| `prescriptions` | 処方箋の枚数 | **処方箋単位**（受付回数ではない） |
| `newPatients` | 新患 | 「初来局」か「その保険での初回」か |
| `onePack` | 一包化加算 | **算定回数**。処方箋単位か剤単位か要確認 |
| `mixing` | 計量混合調剤加算 | 同上 |
| `compounding` | 自家製剤加算 | 同上 |
| `duplicationCheck` | 重複投薬・相互作用等防止加算 | 同上。**疑義照会の下限値** |
| `narcotics` | 麻薬管理指導加算 | |
| `homeVisit` | 在宅患者訪問薬剤管理指導料 | |
| `internalDrugUnits` | 内服薬の剤数（合計） | 調剤料の算定根拠。手間にほぼ比例する |
| `dispenseDays` | 処方日数 → 件数 | **N日後の再来を積み上げる本丸**。日数は実数、丸めない |
| `byDoctor` | 医師コード → 枚数 | 医師マスタと突き合わせるコードが要る |

**「1件」が何を指すかを最初に合意すること。** 処方箋単位か剤単位かで数字が数倍変わる。
定義が違うまま溜めると、あとから遡って直せない。

## 2. 受け口は3経路

どれか1つに賭けない。**シグマが API を出せない可能性が十分にある**ので、
CSV 経由でも同じ場所へ入る作りにしておく。

| 経路 | 使う場面 | 実装 |
|---|---|---|
| **A. CSV 手動アップロード** | まずこれ。API が無くても始められる | 画面からファイルを選ぶ |
| **B. Drive のフォルダ監視** | レセコン側が定時に CSV を吐ける場合 | 時間主導トリガで新着を拾う |
| **C. Web API（doPost）** | シグマが push できる場合 | `/exec` に POST |

**A から作る。** A が動けば、B は「ファイルの置き場が変わるだけ」、
C は「入口が HTTP になるだけ」で、変換と保存は共通。

## 3. 守ること

**冪等にする。** 同じ日を何度取り込んでも結果が変わらない。
`店舗ID × 日付` で upsert し、追記しない。レセコンの値はあとから確定するので、
再取り込みは日常的に起きる。

**出所と取得日時を必ず残す。** どの経路でいつ取った値かが分からないと、
食い違ったときに調べようがない。

**未知の項目を捨てない。** 契約に無いキーが来たら `extra` に丸ごと残す。
捨てると、あとで「その項目も欲しかった」となったとき遡れない。

**欠測と 0 を区別する。** 項目が来なかった日と、0件だった日は別物。
0 で埋めない。

**部分的に壊れたデータで全体を止めない。** 行単位で検証し、
通った行だけ入れて、弾いた行は理由付きで残す。

**認証は共有シークレット。** C を使うなら、`X-Api-Key` をスクリプトプロパティと
突き合わせる。GAS の Web アプリは URL を知られると誰でも叩けるので、
「リンクを知っている全員」で公開するなら必須。

## 4. シグマに確認すること

そのまま渡せるようにまとめてある。

**出せるかどうか**

1. 日次で出せるか。**月次のレセプト集計しか出せない場合、この構想は成立しない**ので最初に確認する
2. 出力形式は CSV か、API か。API ならプッシュ型かプル型か
3. 加算の算定回数を項目別に出せるか（一包化・計量混合・自家製剤・重複投薬相互作用等防止）
4. 処方日数の分布を出せるか（日数ごとの件数）
5. 医師ごとの処方箋枚数を出せるか。医師を識別するコードは何か

**定義の確認**

6. 加算の「1件」は処方箋単位か、剤単位か
7. 処方箋枚数は受付回数か、処方箋の枚数か
8. 締めのタイミングはいつか。値はいつ確定するか。遡って変わることはあるか
9. 店舗を識別するコードは何か

**運用**

10. 追加費用と、対応にかかる期間
11. テスト用のサンプルデータをもらえるか（**これが早くもらえると開発が進む**）
